# سيناريوهات الفحص والتحقق المستندة للمراجع (Reference-Based System Verification Scenarios)
**المشروع:** Nama Invest ERP / Namasoft ERP
**المهمة:** REFERENCE_SKILLS_AND_FULL_SYSTEM_SCAN_ONLY
**التاريخ:** 2026-06-07

يرسم هذا الدليل سيناريوهات تفصيلية تفاعلية لفحص واختبار مطابقة نظام Nama Invest ERP للمعايير العالمية المستخلصة من مراجع الأمان (ASVS)، وممارسات Node.js، والجودة البرمجية، والنظم المحاسبية الكبرى (ERP).

---

## 🏛️ 1. سيناريوهات الفحص الأمني وعزل البيانات (Security & Tenant Isolation Scenarios)

### سيناريو SCN-SEC-001: فحص حظر تسريب بيانات المستأجرين (Cross-Tenant Leakage Verification)
* **الهدف:** التأكد من استحالة وصول مستخدم مستأجر (Tenant A) لبيانات مستأجر آخر (Tenant B) عند محاكاة استدعاء مباشر لـ APIs.
* **خطوات الفحص:**
  1. الدخول بحساب مصادق عليه يتبع لـ `tenant-1`.
  2. استخراج عنوان API محمي مثل `/api/sales/invoices` أو `/api/settings/roles`.
  3. استخدام أداة (مثل Postman أو cURL) لإرسال طلب HTTP GET مع استبدال رقم المستأجر في الترويسة (Header) أو في معطيات الطلب بمعرف مستأجر آخر `tenant-2`.
* **النتيجة المتوقعة والمقبولة:**
  * يرجع النظام كود استجابة `401 Unauthorized` أو `403 Forbidden` بشكل صريح.
  * لا يتم إرجاع أي حقول أو بيانات تخص المستأجر الآخر نهائياً.

### سيناريو SCN-SEC-002: فحص التحقق من الصلاحيات في الخلفية (Server-Side Access Control)
* **الهدف:** التأكد من أن حماية أزرار وشاشات التحكم لا تقتصر على إخفاء الأزرار في الواجهة الأمامية بل تُفرض في الخلفية.
* **خطوات الفحص:**
  1. تسجيل الدخول بحساب مستخدم يحمل دور موظف مبيعات عادي (Sales Employee) لا يملك صلاحية اعتماد القيود المحاسبية.
  2. نسخ مسار الـ API المسؤول عن اعتماد القيود أو الفترات مثل `/api/accounting/periods/lock`.
  3. إرسال طلب HTTP POST لتعديل حالة الفترة باستخدام حساب الموظف.
* **النتيجة المتوقعة والمقبولة:**
  * يرفض الخادم معالجة الطلب فورياً ويرجع كود `403 Forbidden` مع تسجيل محاولة الوصول غير المصرح بها في الـ Audit logs بنظام SIEM.

## 💻 2. سيناريوهات الفحص البرمجي وجودة الأكواد (Code Quality & Performance Scenarios)

### سيناريو SCN-PERF-001: فحص خلو مسارات المعاملات الحية من معطلات الـ Event Loop (Sync Blockers Check)
* **الهدف:** ضمان بقاء الواجهات وسيرفر الطلبات مستجيبين تحت ضغط المعاملات الكبرى بدون تجميد.
* **خطوات الفحص:**
  1. مسح ملفات الـ API الحساسة وتحديداً واجهات نقاط البيع والمحاسبة والمستندات.
  2. التأكد من عدم وجود أي استدعاءات متزامنة لقراءة الملفات مثل `fs.readFileSync` أو مكتبات تشفير تعمل بشكل متزامن يعطل الـ Event Loop.
* **النتيجة المتوقعة والمقبولة:**
  * استخدام كامل ومطلق لـ Async/Await وتمرير المهام الثقيلة (مثل معالجة فواتير ZATCA الضخمة أو توليد ملفات PDF) للعمال الخلفيين (BullMQ Workers).

### سيناريو SCN-PERF-002: فحص تسريبات الذاكرة في شاشات نقاط البيع (POS Long-Run Memory Leak Check)
* **الهدف:** التأكد من بقاء شاشات POS/Restaurant POS مستقرة ولا تسبب كراش للمتصفح عند بقائها مفتوحة طوال فترة مناوبة العمل (Shift) البالغة 12 ساعة.
* **خطوات الفحص:**
  1. فتح شاشة الـ POS في متصفح Chrome وتفعيل أدوات المطورين (Performance / Memory tab).
  2. إجراء 50 عملية بيع وهمية متتالية ومراقبة منحنى استهلاك الذاكرة (JS Heap Size).
  3. التأكد من تحرر الذاكرة وعودتها للمستوى الطبيعي بعد إغلاق النوافذ المنبثقة أو تحديث حالة الطابعة (QZ WebSocket polling).
* **النتيجة المتوقعة والمقبولة:**
  * منحنى ذاكرة مستقر (Sawtooth pattern) دون صعود رأسي مستمر، وتأكيد التخلص الفوري من مراقبي الأحداث (Event Listeners) والمؤقتات عند تفكيك المكونات.

## 📈 3. سيناريوهات الفحص المالي والمحاسبي وحوكمة الأصول (Financial & ERP Scenarios)

### سيناريو SCN-FIN-001: محاولة ترحيل قيد يومية غير متوازن (Unbalanced Journal Entry Prevention)
* **الهدف:** التحقق من صلابة حرس القيد المزدوج في النظام ضد الترحيل غير المتوازن.
* **خطوات الفحص:**
  1. فتح شاشة إدخال قيود اليومية اليدوية.
  2. إدخال بند مدين بقيمة `1000 SAR` وبند دائن بقيمة `990 SAR` (فرق 10 ريال).
  3. محاولة الضغط على زر ترحيل/اعتماد القيد.
* **النتيجة المتوقعة والمقبولة:**
  * يرفض النظام حفظ أو ترحيل المعاملة فوراً، وتظهر رسالة خطأ محاسبية صريحة تفيد بعدم توازن القيد.
  * يمنع حفظ القيد في قاعدة البيانات.

### سيناريو SCN-FIN-002: محاولة التعديل أو الحذف لقيد مالي مرحل (Posted Record Immutability Verification)
* **الهدف:** إثبات عدم قابلية الدفاتر المالية للتلاعب أو التعديل بعد اعتمادها.
* **خطوات الفحص:**
  1. استعلام قيد يومية مسجل في قاعدة البيانات ويحمل الحالة `POSTED`.
  2. محاولة إرسال طلب HTTP PUT أو DELETE لتغيير مبالغ القيد أو حذفه.
* **النتيجة المتوقعة والمقبولة:**
  * يرفض محرك النظام المالي العملية ويرجع خطأ ترحيل صريح. لتعديل القيد، يجب إلزامياً إجراء قيد تسوية عكسي (Reversal Entry).

### سيناريو SCN-FIN-003: محاولة إدخال معاملة مالية في فترة مغلقة (Closed Period Verification)
* **الهدف:** التأكد من حصانة الفترات المالية المغلقة ضد أي حركات متأخرة أو تعديلات بأثر رجعي.
* **خطوات الفحص:**
  1. تحديد فترة مالية مغلقة مسبقاً (مثل يناير 2026).
  2. محاولة إنشاء فاتورة مبيعات أو قيد يومية وتحديد تاريخ المعاملة في يناير 2026.
  3. محاولة حفظ المعاملة.
* **النتيجة المتوقعة والمقبولة:**
  * يفشل فحص الصلاحية الزمني في الخادم فورياً، ويرفض النظام حفظ المعاملة مع توضيح أن الفترة المالية مغلقة ولا يمكن الكتابة فيها.
