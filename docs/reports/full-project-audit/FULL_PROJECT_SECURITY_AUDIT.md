## 1. Tenant Isolation Architecture / بنية عزل المستأجرين

يستخدم النظام معمارية مشاركة الموارد بقاعدة بيانات موحدة وعزل منطقي صارم (**Shared-Schema Multi-Tenant Architecture**) يرتكز على وجود العمود الحاكم `tenantId` في كافة جداول البيانات.

### 🛡️ نقاط القوة المعززة
* يتم جلب وتدقيق المستأجر داخل واجهات الاستعلام الأساسية (API Requests) عبر مستخلص الترويسة الحاكم `requireTenantId` والذي يستخلص سياق العمل بأمان تام.
* إخضاع معظم جداول ومستعلمي استدعاءات البيانات لـ middlewares تمنع تداخل الكيانات.

### ⚠️ الفجوات التشغيلية والثغرات المرصودة (ISS-01)
* **المشكلة**: تفتقر بعض مهام الكرون الخلفية والسكربتات الدورية للفلترة الصارمة بحسب الـ `tenantId` عند إجراء عمليات المسح أو التطهير، وتستعلم بشكل كلي مما يهدد بتداخل الجلسات أو مسح حركات مستأجرين آخرين بالخطأ.
* **الموقع**: `src/app/api/admin/cron/route.ts` & `src/scripts/cron-cleanup.ts`.
* **مستوى الخطورة**: `P1 High`.

## 2. RBAC & Authorization / نظام الصلاحيات المبني على الأدوار

يستند نظام التحكم بالوصول إلى الصلاحيات الدقيقة التي تتجاوز مجرد الأدوار الوظيفية الثابتة (**Granular Permissions Override Roles**).

### 🛡️ نقاط القوة المعززة
* يتم فحص صلاحيات المستخدم بشكل ديناميكي من خلال الاستعلام المتزامن من جدول `UserPermission` والذي يسمح بتعطيل أو تمكين صلاحيات الإضافة، التعديل، والطباعة لكل مستخدم وحظر تجاوزها.

### ⚠️ الفجوات التشغيلية والثغرات المرصودة (ISS-02)
* **المشكلة**: طلبات استرداد رموز المصادقة الثنائية للـ MFA (`MfaRecoveryRequest`) تفتقر لبروتوكول التحقق والاعتماد الثنائي (Dual-Officer Consensus Approval). يمكن لمشرف إداري واحد اعتماد الطلب وإرسال مفاتيح جديدة، وهو ما يمثل ثغرة خطيرة في حال تعرض حساب المشرف للاختراق.
* **الموقع**: `src/app/api/admin/mfa/recovery/route.ts`.
* **مستوى الخطورة**: `P1 High`.

## 3. Secrets Scanning & Git Hygiene / فحص الأسرار والـ Git

تم إجراء مسح معمق وآمن بداخل كامل ملفات المشروع للتحقق من عدم وجود أي تسريب لرموز المصادقة أو المفاتيح الحقيقية:

### 🔍 نتائج الفحص والمطابقة
* **المفاتيح الحقيقية**: لم يعثر الفحص على أي مفاتيح تشفير أو كلمات مرور حقيقية حية خاصة بالخوادم أو بيئة الإنتاج مخزنة بداخل الكود المصدري.
* **مفاهيم الـ Mock**: تحتوي ملفات اختبار الامتثال وهيئة الزكاة على محاكاة تكوينية واضحة خالية من أي أسرار:
  - `src/lib/zatca/zatca-onboarding-engine.ts` يحوي توليداً افتراضياً لـ `MOCK_KEY_FOR_...`.
  - `src/scripts/test-zatca-compliance.ts` يحتوي على صياغة لترويسات مفاتيح افتراضية معماة ومحاكة بالكامل.
* **المجلدات غير المتتبعة**: المجلد `zatca_tmp_local/` ومفاتيح الفحص فيه مستبعدة ومعزولة تماماً بداخل `.gitignore` لمنع دفعها للـ Git بالخطأ.

## 4. API Security & Rate Limiting / أمن الواجهات وحدود الاستخدام

تعد حماية الواجهات ضد هجمات القوة الغاشمة (Brute-Force) وحجب الخدمة خط الدفاع الأول للنظام الحاكم:

### ⚠️ الثغرات المكتشفة وتوصيات الحماية (ISS-08)
1. **واجهات الرفع المفتوحة (Upload APIs)**:
   - **المشكلة**: تفتقر بعض نهايات الرفع الطرفية `/api/upload` للتحقق الحقيقي والمعمق من محتوى الملف الحقيقي (Magic Numbers verification) وتعتمد فقط على لاحقة الملف `extension` أو ترويسة نوع الملف المرسلة بالطلب (MIME-type Header)، مما يسهل رفع ملفات تشغيلية ضارة متنكرة.
   - **مستوى الخطورة**: `P2 Medium`.
   - **الحل المقترح**: فحص ترويسة البايتات الأولى للملف المرفوع عبر مكتبات فحص حقيقية لضمان سلامته قبل حفظه على الخادم.
2. **حدود الاستخدام (Rate Limiting)**:
   - **المشكلة**: غياب محدد استخدام صارم (Rate Limiter) على بوابات الربط واستقبال الـ Webhooks لبعض بوابات الرسائل وبوابات الدفع، مما قد يسهل استغلالها لإغراق طوابير العمل.
   - **مستوى الخطورة**: `P2 Medium`.
   - **الحل المقترح**: تفعيل محدد استخدام معزول عبر Redis لتقييد الطلبات المتكررة بحدود تشغيلية منطقية.
