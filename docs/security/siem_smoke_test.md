# Staging & Production Smoke Test Checklist — SIEM Subsystem

يقدم هذا المستند **قائمة التحقق واختبارات الدخان الفعالة (Smoke Test Checklist)** للتحقق الآمن والتشغيلي من نظام مراقبة الأمان الـ SIEM وكشف الأنماط بعد نشره بالكامل على الخوادم التجريبية (Staging) أو الإنتاجية (Production).

---

## 1. أهداف اختبارات الدخان (Objectives)
التحقق الفعلي من سلامة ومزامنة كامل تدفق البيانات (End-to-End Flow) بين واجهات المستخدم والمحركات الخلفية وقاعدة البيانات دون المخاطرة ببيانات الإنتاج أو تعطيل العمليات المالية الحساسة.

---

## 2. إرشادات السلامة القصوى (Safety Guardrails)
- **ممنوع نهائياً:** استخدام أدوات هجوم تلقائية (مثل Hydra أو Nmap) أو تشغيل حركة مرور كثيفة (Brute Force Traffic) لتجربة الكشف، لأن ذلك قد يؤدي لتفعيل الحظر التلقائي بالـ Firewall وتوقف الأنظمة.
- **ممنوع نهائياً:** التعديل على أي سجل محاسبي أو مالي أو فواتير خلال فترة فحص الأمان.
- **تأمين العزل:** يُجرى الفحص فقط باستخدام الحساب التجريبي المخصص لضابط الأمان (Security Officer) أو المسؤول (Admin).

---

## 3. قائمة التحقق واختبارات الدخان التفصيلية (Smoke Test Checklist)

### **الخطوة 1: التحقق من الوصول للوحة التحكم (Dashboard Access Verification)**
*   **الإجراء:**
    - [ ] قم بتسجيل الدخول بحساب يملك دور `admin` أو `owner` أو `security_officer`.
    - [ ] انتقل إلى المسار المخصص: `/admin/siem`.
*   **النتائج المتوقعة:**
    - [ ] تفتح الصفحة بنجاح مع ظهور التصميم الزجاجي (Glassmorphic Theme) بالكامل.
    - [ ] تظهر إحصائيات الأحجمالي وتوزيع الشدة (CRITICAL, HIGH, MEDIUM, LOW, INFO).
    - [ ] عدم ظهور أي خطأ `403 Forbidden` أو `401 Unauthorized` لحاملي هذه الأدوار الثلاثة.
    - [ ] محاولة الدخول بنفس الرابط عبر حساب كاشير (Cashier) عادي أو محاسب والتأكد من إرجاع رسالة حظر واضحة (`403`).

---

### **الخطوة 2: توليد حدث فشل مصادقة آمن (Safe `AUTH_FAIL` Generation)**
*   **الإجراء:**
    - [ ] افتح نافذة متصفح خفية (Incognito window).
    - [ ] انتقل لصفحة تسجيل الدخول واكتب اسم مستخدم غير موجود أو كلمة مرور خاطئة **مرة واحدة فقط (1 Single Attempt)**.
    - [ ] أو بدلاً من ذلك، حاول إدخال كود ثنائي (MFA OTP) منتهي الصلاحية عند الطلب.
*   **النتائج المتوقعة:**
    - [ ] يرجع النظام خطأ فشل مصادقة للمتصفح.
    - [ ] عد مجدداً للوحة تحكم الـ SIEM بحساب المسؤول، وحدّث البيانات.
    - [ ] يجب أن يظهر حدث جديد بنوع `AUTH_FAIL` ومصدر `audit` أو `mfa` ويحتوي تفاصيل الـ IP والـ User Agent بشكل دقيق ومحاذٍ للحدث الحقيقي.

---

### **الخطوة 3: توليد حدث رفض صلاحية آمن (Safe `RBAC_DENIED` Generation)**
*   **الإجراء:**
    - [ ] قم بتسجيل الدخول بحساب مستخدم عادي (مثال: موظف مبيعات أو كاشير يملك صلاحية بيع فقط).
    - [ ] حاول الوصول المباشر من المتصفح لرابط مالي مقيد (مثال: محاولة جلب تقرير الأستاذ العام `/api/admin/accounting/general-ledger`).
*   **النتائج المتوقعة:**
    - [ ] يرجع النظام فوراً استجابة `403 Forbidden` برمز رسالة الصلاحيات غير الكافية.
    - [ ] عند تحديث لوحة الـ SIEM للمسؤول، يجب ظهور حدث بنوع `RBAC_DENIED` ومصدر `audit` يوثق محاولة الكاشير الدخول للموديول المالي المقيد ومرفقاً بالـ IP والوقت.

---

### **الخطوة 4: التحقق من دقة كشف الأنماط في الواجهة (Pattern Detection Verification)**
*   **الإجراء:**
    - [ ] تفقد الجزء العلوي المخصص لبطاقات الأنماط المشبوهة (Patterns Cards Alert Banner).
    - [ ] ابحث عن ظهور أنماط حية مثل `OFF_HOURS_BYPASS` (في حال قيام أحد المسؤولين بالتخطي بعد 10:00 م بتوقيت الرياض)، أو `RBAC_CRAWL` إذا تم تكرار الرفض.
*   **النتائج المتوقعة:**
    - [ ] تظهر بطاقات الأنماط بالشدة اللونية المناسبة (مثل الأحمر الفاقع للشدة العالية `HIGH`).
    - [ ] يظهر الوصف باللغتين العربية والإنجليزية بوضوح تام تبعاً للغة المحددة في المتصفح.
    - [ ] النقر على زر "التفاصيل" يفتح المودال الجانبي ويعرض كافة بيانات الحدث والـ Metadata الخام المرفقة بشكل منسق.

---

### **الخطوة 5: التحقق من تصدير البيانات (CSV Export Verification)**
*   **الإجراء:**
    - [ ] من الزاوية العلوية للوحة التحكم، انقر على زر **"تصدير" (Export CSV)**.
*   **النتائج المتوقعة:**
    - [ ] يبدأ تحميل ملف الـ CSV فوراً وبسلاسة مطلقة.
    - [ ] افتح الملف وتأكد من احتوائه على الحقول الدقيقة مثل: `ID`, `Timestamp`, `Type`, `Severity`, `Source`, `Actor`, `IP`, `Summary`.
    - [ ] التأكد من خلو ملف التصدير من أي مشاكل تشفير وتوافق لغوي للحروف العربية.

---

### **الخطوة 6: اختبار أداء الـ API وعدم الضغط الزائد (API Performance & Auto-Refresh Check)**
*   **الإجراء:**
    - [ ] قم بتفعيل خيار "تحديث آلي" (Auto-refresh) من الواجهة.
    - [ ] افتح لوحة المطورين في المتصفح (Chrome DevTools) وراقب نافذة الشبكة (Network tab).
*   **النتائج المتوقعة:**
    - [ ] يتم إرسال طلب تصفح وحيد كل 60 ثانية بشكل صامت وغير معطل للمتصفح.
    - [ ] زمن استجابة الـ API (`/api/admin/siem`) لا يتجاوز **50 إلى 150 ملي ثانية (ms)** كحد أقصى نظراً لوجود الفهارس ودقة الاستعلامات المتوازية.
    - [ ] عدم وجود أي تراكم للطلبات أو تسريب للـ Memory في الواجهة الأمامية.

---

## 4. خطة الأمان والتراجع عند الطوارئ (Safety & Rollback Plan)
*   **عزل التأثيرات:**
    نظرًا لأن محرك الـ SIEM يقف في طبقة المراقبة (Read-Only Telemetry Engine) ولا يكتب أو يعدل أي بيانات تشغيلية أو مالية في الإنتاج، فإن احتمالية تأثيره السلبي على النظام تكاد تكون **معدومة**.
*   **خطة التراجع (Rollback Plan):**
    في حال حدوث بطء شديد أو حمل غير متوقع في قاعدة البيانات بسبب كثرة السجلات التاريخية:
    1.  **خطوة 1:** تعطيل لوحة الـ SIEM مؤقتاً في الإنتاج عبر إغلاق المسار الخاص بها في الـ Router.
    2.  **خطوة 2:** مراجعة نافذة وقت الاستعلام وتقليصها إلى **ساعة واحدة** بدلاً من **24 ساعة** لتقليل حجم القراءة من الـ `AuditLog`.
    3.  **خطوة 3:** إيقاف الـ Auto-refresh مؤقتاً من كود الواجهة لحين صيانة الفهارس على قاعدة البيانات الإنتاجية.
