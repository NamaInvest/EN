# خطة تصميم وتطوير حامل الاختبار (Test Harness) لنظام Nama Invest ERP

يوضح هذا المستند التصميم الهيكلي لحامل الاختبار الآمن لتنفيذ سيناريوهات فحص الجودة والأمان والأداء بشكل تلقائي مع المحافظة على سلامة بيئة الإنتاج وقاعدة البيانات الحية.

---

## 🏛️ 1. الهدف الأساسي
تمكين المطورين وأنظمة التحقق الآلي من تشغيل الـ 19 سيناريو متبقياً في نظام Nama Invest ERP في بيئة معزولة بالكامل دون قلق من حدوث ترحيل مالي خاطئ، تسريب بيانات بين المستأجرين (Cross-Tenant Leakage)، أو تعديل سجلات الإنتاج.

---

## 🏗️ 2. الطبقات المقترحة لحامل الاختبار (Architecture Layers)

### 1. طبقة اختبارات الوحدة (Unit Test Harness)
- **الهدف:** اختبار دوال التحقق الحسابية، فحص الصياغات (مثل IBAN وسجل التجاري)، وقواعد المنطق المحاسبي البحتة.
- **التنفيذ:** استخدام Vitest دون تفعيل أي خادم أو قاعدة بيانات.
- **الأمان:** آمنة بنسبة 100% ولا تتطلب صلاحيات.

### 2. طبقة عقود واجهات البرمجة (API Contract Harness)
- **الهدف:** اختبار استجابة مسارات الـ API (مثل `/api/accounting/coa`) ورفض الطلبات غير المصرحة.
- **التنفيذ:** استخدام `vi.mock` لمحاكاة الـ Request والـ Session (مثل Clerk session)، وتمرير سياق مستأجر وهمي.
- **الأمان:** يتم محاكاة اتصال قاعدة البيانات بالكامل للتأكد من عدم إجراء عمليات حية.

### 3. طبقة اختبار دمج البيانات المعزولة (Integration Test DB Harness)
- **الهدف:** اختبار ترحيل المستندات الحقيقي (مثل ترحيل قيود اليومية أو خفض المخزون) وقياس الأثر المحاسبي الفعلي.
- **التنفيذ:** استخدام قاعدة بيانات اختبار مؤقتة (Dockerized SQLite أو Ephemeral PostgreSQL) منفصلة تماماً ومحددة بمتغير بيئة `DATABASE_URL` خاص بالاختبارات فقط.
- **الأمان:** تفعيل التراجع التلقائي عن المعاملات (Transaction Rollback) بعد كل اختبار لضمان بقاء قاعدة البيانات نظيفة وجاهزة للاختبار التالي.

### 4. طبقة اختبار القبول التفاعلي (Playwright Smoke Harness)
- **الهدف:** اختبار شاشات الكاشير وخرائط الطاولات والمظهر العام للواجهات.
- **التنفيذ:** تشغيل Playwright لمحاكاة نقرات المستخدم وتصفحه.
- **الأمان:** قصر الاختبارات على الملاحة للقراءة فقط (Read-only Navigation) وتجميد أي عمليات نقر حيوية قد تؤدي لإنشاء فواتير أو إهلاك أصول حقيقية.

### 5. سجل التشغيل اليدوي (Manual Only Registry)
- **الهدف:** للعمليات التي يستحيل أتمتتها محلياً بأمان (مثل الإرسال الفعلي لـ ZATCA، الصرف المالي الفعلي للرواتب WPS، أو الدفع البنكي الحي).
- **التنفيذ:** توثيق قوائم تحقق يدوية تشغل في بيئة Staging شبيهة بالإنتاج قبل الإطلاق الفعلي.

---

## 🔒 3. بوابات السلامة والتحقق (Safety Gates)

1. **بوابة عزل قاعدة البيانات (DB Isolation):** حظر تشغيل أي اختبار تكامل ما لم يكن متغير البيئة `NODE_ENV` يشار إليه بـ `test`.
2. **بوابة عزل المستأجر (Tenant Isolation Mock):** إجبار كافة استعلامات Prisma على تضمين `tenantId` والتحقق التلقائي في الموك من وجود سياق للمستأجر لجميع عمليات الاستعلام والتعديل.
3. **بوابة الصلاحياتRBAC Mock:** إمكانية تزوير وتبديل أدوار المستخدمين (مثل كاشير، محاسب، مدير مالي) للتحقق من رفض أو قبول الصلاحيات.
4. **بوابة تدقيق السجلات (AuditLog Assertion):** التحقق التلقائي من تسجيل الحركات الحساسة في جدول `AuditLog` بعد كل عملية تعديل ناجحة.
5. **بوابة الفترة المغلقة (Period Lock Assertion):** التحقق من رفض العمليات في التواريخ المغلقة مالياً.
6. **بوابة التراجع وتأكيد البيانات (Rollback & Seed Cleanup):** مسح بيانات الاختبار المولد تلقائياً (Factories Seed) وتفعيل التراجع لتجنب تضخم قاعدة بيانات الاختبار.

---

## 📂 4. هيكل الملفات المقترح لحامل الاختبار (Harness Files)

نقترح إنشاء الملفات التالية تدريجياً لتنظيم حامل الاختبار تحت مسار `tests/harness/`:

- `tests/harness/auth.ts`: لتزوير وتوفير جلسات Clerk وصلاحيات مستخدم الاختبار.
- `tests/harness/tenant.ts`: لإنشاء سياق وعزل المستأجر الوهمي لعمليات الـ API.
- `tests/harness/rbac.ts`: لتوفير أدوار المستخدمين ومطابقة الصلاحيات.
- `tests/harness/prisma-mock.ts`: لتوسيع محاكاة Prisma ومراقبة الاستعلامات الصادرة.
- `tests/harness/request.ts`: لبناء طلبات HTTP وهمية وتمرير الترويسات (Headers).
- `tests/harness/seed.ts`: لتوفير بيانات جرد أولية ودليل حسابات افتراضي نظيف لكل دورة اختبار.
- `tests/harness/rollback.ts`: لإدارة بدء وإنهاء معاملات التراجع في قاعدة بيانات الاختبار.
- `tests/harness/assertions.ts`: لتوفير دوال تأكيد مخصصة (مثل `assertUnauthorized`).

---

## 🌊 5. موجات تنفيذ حامل الاختبار (Implementation Waves)

* **Wave H1:** هيكلة واجهات المحاكاة فقط (Mock-only Harness) لتزوير الجلسات وسياق المستأجر بشكل موحد.
* **Wave H2:** بناء حامل عقود واجهات البرمجة (API Contract Harness) لتمكين اختبار مسارات الـ API للقراءة والتعديل المزور.
* **Wave H3:** تهيئة خادم قاعدة بيانات الاختبار المعزول (Dockerized / Isolated Test DB Harness) وتطبيق معاملات التراجع التلقائي.
* **Wave H4:** تهيئة اختبارات Playwright للملاحة الآمنة والـ tooltips.
* **Wave H5:** بناء نماذج التحقق وقوائم الفحص اليدوية للعمليات غير القابلة للأتمتة بأمان.
