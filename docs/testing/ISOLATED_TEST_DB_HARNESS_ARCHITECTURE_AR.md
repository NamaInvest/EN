# هندسة Isolated Test DB Harness

## الهدف
تمكين اختبارات تكامل آمنة بدون لمس الإنتاج وبدون DB حقيقي غير معزول.

## مبادئ السلامة
- لا production.
- لا .env إنتاجي.
- لا migrations مباشرة.
- لا prisma db push.
- لا live posting.
- كل اختبار إما rollback أو disposable DB.
- كل tenant test data معزولة بالكامل.
- كل seed يكون deterministic.

---

## طبقات التصميم

### 1. Database Isolation Layer (طبقة عزل قاعدة البيانات)
- قراءة `TEST_DATABASE_URL` فقط.
- يمنع تماماً الاتصال بـ `DATABASE_URL` الأساسي في بيئة الاختبار.
- فحص صياغة الـ URL ومنع الاتصال في حال عدم وجود كلمة `test` أو `disposable` في اسم قاعدة البيانات.
- اشتراط وجود المتغير البيئي `TEST_MODE=true` صراحةً.

### 2. Tenant Seed Layer (طبقة تهيئة المستأجرين)
- `createTestTenant`: توليد مستأجر جديد بمعرف عشوائي معزول.
- `createTestUser`: إنشاء مستخدمين افتراضيين مع تزويد الصلاحيات والأدوار.
- `createTestRole`: تهيئة أدوار اختبار مخصصة.
- `createTestPermissions`: تحديد صلاحيات دقيقة لكل دور.
- `createTestFiscalPeriod`: فتح فترة مالية مخصصة لاختبارات اليومية.

### 3. Finance Seed Layer (طبقة تهيئة المالية)
- تهيئة شجرة الحسابات SoCPA المعتمدة.
- توليد قيود يومية وهمية.
- تهيئة قفل الفترات المالية (Period Lock) للتواريخ المطلوبة.
- تهيئة الفواتير المفتوحة للمطابقات وتنبيهات التحصيل.

### 4. Sales/POS Seed Layer (طبقة تهيئة المبيعات ونقاط البيع)
- إنشاء عملاء افتراضيين.
- إنشاء منتجات مع أسعارها الافتراضية.
- إعداد مسودات فواتير المبيعات.
- محاكاة ورديات الكاشير النشطة وتفاصيل الطاولات لوردية المطعم.

### 5. Inventory Seed Layer (طبقة تهيئة المخازن)
- تهيئة المستودعات (Source / Destination Warehouses).
- إدراج الأصناف والباركود التابع لها.
- تهيئة أرصدة المخزون الافتراضية وتثبيت متوسط التكلفة.

### 6. Purchases/Approvals Seed Layer (طبقة تهيئة المشتريات والموافقات)
- تهيئة الموردين المعتمدين.
- إدراج مسودات أوامر الشراء وسندات الاستلام (GRN).
- إعداد مصفوفة الموافقات وسلسلة المدراء المعتمدين.

### 7. Rollback Layer (طبقة التراجع البرمجي)
- تفعيل معاملات التراجع التلقائي (`Prisma transaction rollback`) بعد نهاية كل فحص.
- تفريغ أو مسح الجداول المؤقتة والبيانات المضافة (Truncate/Delete) في بيئة الـ afterEach.

### 8. Assertions Layer (طبقة التحققات المالية والأمنية)
- `assertBalancedJournal`: التحقق الحسابي من توازن قيود اليومية.
- `assertPeriodLocked`: التحقق من حظر الكتابة في فترات مغلقة.
- `assertTenantScoped`: التأكد من انحصار البيانات في نطاق الـ tenant المعني وعدم وجود تسريبات.
- `assertAuditLogged`: التحقق من كتابة سجلات التدقيق في جدولي AuditLog.
- `assertNoProductionUrl`: حظر استخدام أي عناوين أو خوادم خارجية إنتاجية.

## Parallel Implementation Waves

- **H1: Test DB Safety Guard only**
  - وضع حواجز حماية وتدقيق الاتصالات بقاعدة البيانات ومنع الاتصال بقاعدة الإنتاج.
- **H2: Seed factories docs + mock-only tests**
  - توثيق وبناء خطط التهيئة وتوليد البيانات الافتراضية مع اختبارات محاكاة آمنة.
- **H3: Finance integration harness**
  - إعداد بيئة اختبار المحاسبة وتوليد قيود الإهلاك وإقفال الفترات التكاملي.
- **H4: Sales/POS integration harness**
  - تهيئة بيئة اختبار المبيعات والتحقق من الكميات وفواتير البيع ومرتجع المبيعات.
- **H5: Inventory integration harness**
  - تهيئة اختبارات نقل البضائع وحركات التحويل وتسوية الفروقات المخزنية.
- **H6: Purchases/Approvals integration harness**
  - تهيئة اختبارات مرتجع المشتريات وسلسلة الموافقات التراكمية.
- **H7: Compliance manual-only registry**
  - توثيق مسار الاختبار اليدوي وتدقيق الفواتير المعتمدة زكاة وملفات حماية الأجور الحقيقية.
