# 04 - حماية الـ APIs وعزل المستأجرين (API Protection & Tenant Isolation)

> **آخر تحديث:** 2026-06-02 | **معيار الأمن القومي السحابي للمشروع** | **ثابت معتمد**

---

## 📌 فلسفة أمن المستأجرين (Tenant Isolation)
في نموذج SaaS ERP متعدد الشركات، يمثل تسريب البيانات بين المستأجرين (**Cross-Tenant Data Leakage**) كارثة أمنية وحاسوبية كبرى. لذلك، يتم تطبيق سياسة أمان صارمة تعزل كل مستأجر عزلاً تاماً ومنيعاً على مستوى المعاملات، الذاكرة، والاستعلامات.

---

## 🛡️ المعالجات التقنية المعتمدة للأمان والعزل

### 1. غلاف الحماية المركزي `withRoute`
كافة مسارات الـ API الحساسة (البالغ عددها 887 مساراً) يجب أن تمر عبر الغلاف أو الديكوريتور المركزي `withRoute`. يقوم هذا الغلاف تلقائياً بالمهام التالية:
- التحقق من جلسة المستخدم وهويته المصرحة.
- استخلاص معرف المستأجر الفريد (`tenantId`) مباشرة من رمز التوثيق المشفر (JWT Cookie) ومنع استقباله أو الوثوق به من جسم الطلب (`body`) أو معامل الاستعلام (`query`) لتجنب الاختراق والتزييف.
- التحقق من صلاحيات الأدوار المحددة (RBAC) للمسار المطلوب.

### 2. محدد قاعدة بيانات المستأجر `getPrisma(req)`
يُحظر تماماً استدعاء Prisma Client العام المباشر (`prisma.model.findMany`) في مسارات الـ API. يجب استخدام المساعد الذكي `getPrisma(req)` أو `getPrisma(tenantId)` الذي يضمن:
- توجيه الاستعلام لقاعدة البيانات المحددة للمستأجر (إذا كانت بنية التوزيع تعتمد قواعد بيانات منفصلة).
- حقن استعلام تصفية تلقائي يضمن عدم استرجاع أي سجل لا ينتمي للمستأجر الفعلي (`tenantId`).
- التحكم الكامل في مستودع الاتصالات (Connection Pool) وتفادي هدر الموارد.

---

## 🚫 محظورات الاستعلام المباشر و raw SQL
1. **منع الـ Raw Queries دون تصفية**: يمنع منعاً باتاً كتابة أي استعلام قواعد بيانات خام (`prisma.$queryRaw` أو SQL مباشر) دون تصفية صريحة ومباشرة لمعرف المستأجر (`tenantId`) ومعالجة المعاملات المدخلة لتجنب ثغرات SQL Injection.
2. **منع Direct Prisma Client**: يحظر استخدام `new PrismaClient()` بشكل متكرر في الكود لتفادي استهلاك موارد الخادم وحدوث تسريبات اتصالات، ويجب استخدام المساعد المركزي المعزول للـ Tenants.
3. **عدم الوثوق بمعرف المستأجر الممرر بالطلب**: يمنع قبول `tenantId` كمعامل مدخل في الـ POST/PUT body أو GET query للمسارات المحمية، ويجب سحبه حصراً من الـ Token المشفر بعد فك ترميزه على الخادم.

## 📊 تصنيف مسارات الـ API الأمنية

يتم تصنيف مسارات النظام البرمجي إلى الفئات الأمنية الصارمة التالية:

| التصنيف الأمني | الوصف | قيود الصلاحية والأمان | أمثلة للمسارات |
| ------------- | ----- | --------------------- | -------------- |
| `PUBLIC` | مسارات عامة لا تتطلب مصادقة. | مفتوحة للجميع، ممنوع اتصالها ببيانات ماليّة أو داخلية. | مسار تسجيل الدخول، صفحة الهبوط. |
| `AUTH_REQUIRED` | مسارات تتطلب مستخدماً مسجلاً. | التحقق من صحة الـ Token وجلسة التشغيل. | تعديل الملف الشخصي، تفضيلات المستخدم. |
| `TENANT_REQUIRED`| مسارات مرتبطة بمستأجر وشركة محددة. | التحقق من التوثيق وحقن `tenantId` من الـ Token إجبارياً. | استرجاع فواتير المبيعات، كشف الحساب. |
| `FINANCIAL_CRITICAL`| مسارات ترحيل مالي وتعديل دفاتر. | تتطلب مصادقة قوية، التحقق من فترات مقفلة وتدقيق الموافقات. | ترحيل استبعاد الاستثمارات، اعتماد القيود. |
| `ADMIN_ONLY` | مسارات لإدارة النظام والتهيئة العامة. | تتطلب دور مدير النظام (System Admin) والتحقق من RBAC. | إعداد لوحة تحكم الخادم، إضافة عملات جديدة. |
| `SYSTEM_INTERNAL`| مسارات الاتصال الداخلي والـ CRON. | محمية بمفاتيح أمان سرية مشفرة وصعبة التخمين (Internal Secret Key). | مسارات معالجة الطوابير، فحوص المراقبة. |

## 🔬 مصفوفة تدقيق حماية المسارات (Phase 3)
كجزء من أعمال المرحلة 3 اللاحقة، سيتم توليد وفحص مصفوفة أمن المسارات بالكامل لحصر أي مسار شاذ وتصفير أي استثناءات غير موثقة، لضمان متانة أمنية كاملة بنسبة 100% للنظام السحابي.
