## 3. التدقيق الفني والأمني (Technical & Security Audit)

* **هل يوجد Prisma مباشرة داخل الـ UI؟**
  * **لا**، جميع صفحات الـ UI الحالية تستخدم `fetch` للاتصال بـ APIs ولا تستدعي `PrismaClient` بشكل مباشر، وهو ما يتماشى تماماً مع المعايير المعمارية للمشروع.
* **هل يوجد بيانات وهمية (Mock Data)؟**
  * في **Manufacturing**: تستخدم الـ API الفعلي مباشرة مع قيم افتراضية في حالة عدم توفر البيانات.
  * في **HR**: تستخدم أرقاماً ثابتة (245 موظف، 8 وظائف، 12 مستند منتهي) وبيانات وهمية لآخر التعيينات. سنقوم باستبدالها بـ `fetch` حقيقي من الـ APIs المتاحة.
  * في **Payroll**: سنقوم ببناء الداشبورد الجديدة مباشرة بالاتصال بـ API معاينة المسير لمعرفة أرقام الموظفين والرواتب الفعلية.
* **هل يوجد مسارات حساسة (Sensitive Routes)؟**
  * نعم، تحتوي مسارات مثل `/api/hr/payroll/run` و `/api/hr/employees` على عمليات POST و POST/PUT للكتابة وتعديل الحسابات أو التأثير على القيود المحاسبية.
  * **الإجراء الوقائي**: لن نقوم بطلب أو استخدام أي طريقة كتابة (POST/PUT/PATCH) في صفحات الـ UI للداشبوردات، وسنكتفي بالاستعلامات الآمنة (GET) فقط.

## 4. توصيات التنفيذ الآمن والجميل (Safe & Premium Implementation Plan)

1. **الالتزام الكامل بـ Tenant Guard**:
   * عدم إرسال `tenantId` من المتصفح نهائياً، والاعتماد بالكامل على الـ Token والـ Session في السيرفر لتحديد الـ Tenant بشكل تلقائي وآمن.
2. **عزل وتأمين منطق العمل الحساس**:
   * منع تعديل أو استدعاء أي محرك احتساب مالي (Costing / Payroll / Auto-Journal) أو فك قفل الفترات المالية (Period-Lock).
3. **التصميم الجمالي الراقي (Ultra-Premium Aesthetics)**:
   * استخدام لوحة ألوان متناسقة، وتأثيرات انتقال ناعمة (Micro-animations)، وتوفير حالات واضحة للتحميل والخطأ والبيانات الفارغة (Loading/Error/Empty States).
4. **تجنب التعديلات الخارجية**:
   * لا تعديل في الـ Prisma Schema أو منطق الأعمال المحاسبي.
   * لا استخدام لأوامر Git التلقائية (add/commit/push).
